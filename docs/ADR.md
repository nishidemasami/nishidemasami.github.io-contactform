# アーキテクチャ決定記録 (ADR)

このドキュメントでは、プロジェクトにおける重要なアーキテクチャ上の決定事項（Architecture Decision Records: ADR）を記録します。これにより、なぜその技術や設計が選ばれたのかという「背景とコンテキスト」を後から把握できるようにします。

---

## ADR-001: サーバーレス・アーキテクチャ (AWS SAM) の採用
- **ステータス**: 採用済み (Accepted)
- **コンテキスト**: コンタクトフォームはアクセス頻度の増減が激しく、サーバーの常時稼働はコストパフォーマンスが悪い。また、インフラのコード化 (IaC) と迅速なデプロイが求められていた。
- **決定**: AWS Serverless Application Model (SAM) を使用して、API GatewayとLambdaを中心としたサーバーレスアーキテクチャを採用する。
- **結果**:
  - インフラ構成が `template.yaml` に集約され、管理が容易になった。
  - 使用した分だけの課金となり、ランニングコストが最適化された。
  - コールドスタートの影響を考慮したランタイム選定が必要になった。

## ADR-002: Lambdaランタイムとしての Rust の採用
- **ステータス**: 採用済み (Accepted)
- **コンテキスト**: AWS Lambdaを使用する際、コールドスタート時間を短縮しつつ、高いパフォーマンスとメモリ効率を実現する必要があった。
- **決定**: Lambdaのランタイムに `provided.al2023` (カスタムランタイム) を利用し、実装言語として Rust を採用する。
- **結果**:
  - 高速な起動と低メモリフットプリントを実現した。
  - 強い静的型付けとメモリ安全性により、ランタイムエラーのリスクを低減した。

## ADR-003: データベースとしての Amazon Aurora DSQL の採用
- **ステータス**: 採用済み (Accepted)
- **コンテキスト**: スケーラビリティが高く、サーバーレスアーキテクチャと親和性の高いリレーショナルデータベースが必要だった。
- **決定**: IAMベースの認証 (DB Connect) をサポートし、サーバーレスで提供される Amazon Aurora DSQL を採用する。マイグレーションには Liquibase、ORMには SeaORM を利用する。
- **結果**:
  - データベースのパスワード管理が不要になり、セキュリティが向上した。

## ADR-004: フロントエンドフレームワークとしての Next.js の採用
- **ステータス**: 採用済み (Accepted)
- **コンテキスト**: 将来的な拡張性や、静的サイト生成 (SSG) / サーバーサイドレンダリング (SSR) の選択肢を持つモダンなフロントエンド環境が必要だった。
- **決定**: Next.js (App Router) を採用し、`pnpm` でパッケージ管理を行う。デプロイメントは静的エクスポート (`out` ディレクトリ) を Cloudflare Pages などへ配信する形式を取る。
- **結果**:
  - UIコンポーネント (Amplify UI) との親和性が高く、素早いプロトタイピングが可能になった。
